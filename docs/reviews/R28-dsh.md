5. **R28.3 — the manifest.** I argue for CC's shape: one JSON file per book, a `spine` array in reading order with one object per spine item `{href, class, chapter?, reason?}`, plus a separate `edition` object (title, translator, year, source file name). The class values are exactly `body`, `structural`, `not-the-author`; no `unclassified` value (M10); `chapter` required for `body` (M8); `reason` required for both non-body classes (M7); the `edition` block is never an entry (F6b).
   - **The array is the right container, if its order is checked.** Phase 1 compares the array's hrefs to the OPF spine index by index: same length, same href at each position. A missing entry is a missing href; an extra entry is an extra href; a duplicate href is a format error. A map keyed by href is the alternative: direct absence and no duplicate keys, but it loses the reading-order comparison and cannot show a reordered manifest. I prefer the array for the one-for-one check.
   - **Against and limits.** JSON has no comments; that is the point — the `reason` is data, printed by the report and hashed with the manifest, while a comment is neither and can drift. TOML is stdlib for reading and allows comments; it is a legitimate alternative, but the array-in-order shape and the reason-as-data property are easier to state and check in JSON. YAML is not stdlib. The manifest is hashed as a file, so the format does not change `version_id`; the choice is about review and checking, not identity. This is an argument, not a decision.
